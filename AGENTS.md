# True Proxy

## Назначение

True Proxy — легковесное настольное приложение для прозрачной маршрутизации TCP,
UDP выбранных приложений через SOCKS5; DNS разрешает Windows. Основной сценарий — замена
Proxifier: пользователь выбирает процессы и направляет их трафик в SOCKS-порты
своего VPN. Разные приложения и разные правила могут использовать разные
SOCKS-серверы и порты.

Первая целевая платформа — Windows, поставка — готовое к запуску приложение
в формате `.exe`. При проектировании учитывать последующую поддержку macOS.

## Главные требования

### Легковесность и скорость

- Приложение должно быть суперлегковесным и очень быстрым. Это обязательное
  требование, влияющее на выбор стека, библиотек и архитектуры.
- Минимизировать размер дистрибутива, потребление RAM и CPU, время запуска,
  задержку соединений и накладные расходы на передачу трафика.
- Предпочитать нативный или компилируемый стек и минимальный набор зависимостей.
  Не использовать Electron и не включать отдельный Chromium ради интерфейса.
- Сетевой слой должен работать независимо от отрисовки интерфейса. Закрытое
  окно не должно поддерживать ненужные циклы отрисовки и частый опрос состояния.
- Не передавать пакеты через UI, скриптовый мост или IPC по одному пакету.
  Правила применять в сетевом слое; для интерфейса агрегировать статистику.
- Ограничивать объем журналов, историю соединений и очереди событий.
  Подробная диагностика должна включаться отдельно.
- Проверять легковесность измерениями: запуск, память и CPU в трее,
  пропускная способность и задержка. Не выдавать предположения за результаты.

### Интерфейс и жизненный цикл

- Минималистичный современный UI с понятной настройкой прокси и правил.
- Основной сценарий: запуск приложения включает маршрутизацию; приложение
  продолжает работать в системном трее после закрытия основного окна.
- На главной — большая кнопка запуска/остановки маршрутизации и таймер сессии.
- Наличие приложения в трее означает, что оно запущено. По умолчанию оно активно;
  ручную паузу и ошибку показывать явно в значке трея и интерфейсе.
- Предусмотреть меню трея: открыть окно, включить/приостановить, выйти.
- Полный выход должен остановить перехват и корректно освободить измененные
  приложением маршруты и сетевые ресурсы.
- Не показывать статус «включено» до подтверждения запуска сетевого слоя.
  При его неожиданном завершении сразу отображать ошибку.
- Не допускать конфликтующих экземпляров приложения и сетевого слоя.

### SOCKS и сетевой трафик

- Поддерживать несколько SOCKS5-подключений: название, адрес, порт и, при
  необходимости, аутентификация.
- Прозрачно обрабатывать TCP и UDP выбранных приложений; обычный DNS
  оставлять системному резолверу согласно разделу DNS. Приложения не должны
  требовать собственной настройки прокси.
- Поддержку UDP проверять отдельно: SOCKS5-сервер должен поддерживать
  `UDP ASSOCIATE`. Наличие работающего TCP-прокси не означает поддержку UDP.
- Не отправлять трафик напрямую при ошибке прокси без явного разрешения
  пользователя в настройках или правилах.
- Предусмотреть IPv4 и IPv6; исключить незаметный обход правил через IPv6.
- Исключать зацикливание собственных соединений сетевого слоя и соединений
  к SOCKS-серверам. Не исключать произвольно все процессы с похожим именем.
- Подтвержденный IP Helper владелец PID 4 имеет имя System и пустой путь:
  OpenProcess(System) недоступен. Пропускать его через обычный движок правил,
  без автоматического Direct для PID 4/SMB/LAN и без выдуманного полного пути.
  Ошибки определения остальных владельцев не заменять этой идентичностью.
- Изменение системного HTTP-прокси само по себе не удовлетворяет требованиям
  перехвата TCP, UDP и трафика отдельных процессов.

### Гибкие правила маршрутизации

- Поддерживать упорядоченные правила, их включение/выключение и изменение
  приоритета. Первое совпавшее включенное правило определяет действие.
- Предусмотреть действия: выбранный SOCKS5-прокси, прямое соединение,
  блокировка. Действие по умолчанию для несовпавшего трафика задается явно.
- Предусмотреть условия по процессу: имя исполняемого файла и полный путь.
  Учитывать дочерние процессы как отдельные процессы, если не задана явная
  политика их наследования.
- Предусмотреть условия по доменам и суффиксам доменов, IP/CIDR, портам и
  диапазонам портов, протоколам TCP/UDP.
- Разные типы условий внутри правила объединять через AND, значения одного
  типа — через OR. Семантика должна быть одинаковой в UI и сетевом слое.
- DNS использует Windows; отдельные DNS-маршруты в правилах не настраиваются.
- Проверять корректность правил и ссылок на прокси до применения. Не удалять
  используемый прокси без явного разрешения зависимостей в конфигурации.
- Изменение правил должно иметь понятный эффект на новые и существующие
  соединения. Если требуется переподключение, явно сообщать об этом.

### DNS

- Текущее решение пользователя: использовать системный резолвер Windows;
  главный приоритет — корректное проксирование TCP и UDP приложений.
- DNS по TCP/UDP на порту 53 передавать напрямую без замены DNS-сервера,
  даже если в старом профиле были настройки DNS через SOCKS. DoH/DoT остаются
  обычным трафиком приложения и следуют его TCP/UDP-правилам.
- Не менять DNS адаптеров, системный HTTP-прокси и таблицу маршрутов.
  Устаревшие DNS-поля профилей читать для совместимости, игнорировать в работе
  и не записывать при новом сохранении.
- Не использовать DLL injection, API hooks, подмену dnsapi.dll или отключение
  защиты игры. Исследование Fake-IP отложено и не входит в продукт.
- Доменные условия работают по ограниченному TTL-кэшу наблюдаемых DNS-ответов
  UDP/TCP. Отсутствие имени из-за старого системного кэша, DoH или подключения
  по IP — существенное ограничение; не обещать универсальную доменную маршрутизацию.
- В редакторе отличать точное имя example.com от *.example.com (домен и поддомены).
  Для всей игры рекомендовать правило по EXE без ограничений доменов/IP/портов.
- В журнале показывать правило и известные DNS-имена либо явно неизвестное имя.

## Архитектурные ориентиры

- Основной язык проекта — Rust. Сетевое ядро, модель конфигурации, движок правил
  и платформенную интеграцию реализовывать на Rust; собирать нативное приложение.
- Для UI предпочтителен Slint: интерфейс без WebView с поддержкой Windows и
  macOS. Окончательно закрепить UI-библиотеку и renderer после небольшого
  прототипа с проверкой трея, скрытия окна, памяти, запуска и размера сборки.
  Учитывать требования выбранной лицензии Slint при распространении.
- Выбирать зависимости и механизм перехвата отдельно по результатам проверки
  TCP/UDP, атрибуции процессов, DNS, IPv6 и поведения при остановке.
  Сам по себе выбор Rust не решает задачу прозрачного перехвата.
- Изолировать `unsafe` и FFI в небольших платформенных модулях с описанными
  инвариантами. Основную логику приложения писать на безопасном Rust.
- Разделять модель конфигурации, движок правил, платформенный перехват,
  управление жизненным циклом и UI.
- Windows-специфичный перехват и управление правами изолировать за платформенным
  интерфейсом. Общая модель правил не должна зависеть от Windows API.
- Не писать собственный драйвер без обоснованной необходимости. При выборе
  готового движка или драйвера проверять поддержку TCP/UDP, атрибуции процессов,
  DNS, IPv6, условия распространения и влияние на размер и ресурсы.
- По запросу пользователя обычный запуск Windows автоматически повышает права
  через UAC до создания UI. Не повышать права в безопасных режимах диагностики,
  smoke и замера. При повышении не передавать --enable без явного CLI-флага.
  В дальнейшем учитывать отдельный привилегированный сетевой компонент.
- Хранить настройки локально и применять их атомарно после валидации.
  Пароли прокси защищать средствами платформы и не выводить в журналы.
- Не включать телеметрию, облачные зависимости и фоновые сетевые запросы,
  не необходимые для основной работы, без отдельного требования пользователя.
- Пользователь отдельно запросил автообновления и публичный репозиторий
  github.com/duoxik/true-proxy. Проверять стабильные GitHub Releases при старте
  и раз в 6 часов; возможность выключения и ручной проверки обязательна.
  Отдельные коммиты без релиза не считать доступной установкой. Уведомление и
  кнопка обновления — в UI; загрузка/установка только по явному нажатию.
  До установки пользователь вручную приостанавливает маршрутизацию.
  Проверять HTTPS-хосты GitHub, размер, SHA-256 и PE x64; неизвестный/поврежденный
  файл не запускать. Не встраивать GitHub-токены в клиент. Настройки обновлений
  хранить отдельно от сетевого профиля. Проверки обновлений не должны мешать backend.
- Установщик — копия собственного EXE, без shell-команд и внешнего сервиса.
  Путь назначения получать из дескриптора родительского процесса с проверкой
  времени создания и хеша старого EXE. Дождаться его выхода; атомарная замена
  и восстановление старого EXE при невозможности запуска нового обязательны.
  Не путать успешный spawn с проверкой здоровья приложения после запуска.

## Порядок работы над проектом

### Текущая реализация и команды

- Основной бинарник: `src/main.rs`; контроллер UI: `src/app.rs`; интерфейс:
  `ui/app.slint`. Общие конфигурация, правила, SOCKS5, DNS и учет трафика
  находятся в отдельных Rust-модулях. Windows backend: `src/platform/windows/`.
- Используется Slint 1.18.1 с software renderer и нативным треем. WinDivert
  2.2.2 загружается динамически; его DLL, подписанный драйвер и лицензия встроены
  в EXE и атомарно извлекаются в локальный runtime при необходимости. Полная
  заменяемая пара DLL/SYS рядом с EXE имеет приоритет; поиск по CWD запрещен.
  Не подменять этот backend запуском внешнего Go-движка.
- `scripts/dev.ps1 check`, `test`, `clippy`, `smoke`, `build`, `package` —
  команды разработки и сборки. Локальные инструменты находятся в игнорируемой
  `.tools`; `scripts/bootstrap.ps1` готовит их без изменения глобального PATH.
- `smoke` и обычные тесты не открывают WinDivert и не меняют сеть пользователя.
  `driver_abi` с `--ignored` проверяет только функции DLL и синтаксис фильтров.
  Эти проверки не доказывают работоспособность прозрачного перехвата.
- Тест updater_install заменяет только собственные фикстуры в Temp и запускает
  безопасный payload. В debug EXE есть режим --exercise-update для этого теста;
  в release он отсутствует. Диагностика --check-updates/--download-update делает
  только разрешенные запросы GitHub и проверку файла, без установки/UAC/перехвата.
- `scripts/dev.ps1 dns-probe` собирает только исследовательские examples:
  два собственных процесса, локальный Fake-DNS, два mock SOCKS и реальное
  определение PID через IP Helper. Настройки DNS задаются только внутри самих
  тестовых процессов; настройки адаптеров и чужие процессы не изменяются.
  Прототип не входит в продуктовый EXE и не проверяет перехват WinDivert.
- Использовать темную палитру `Theme` в `ui/app.slint`. У кнопок `FocusScope`
  имеет нулевую ширину, чтобы не перехватывать нажатия поверх `TouchArea`.
  Проверять первый клик событиями мыши; вызов callback напрямую не проверяет
  кликабельность. UI-тесты используют только dev-зависимость Slint Testing.
- Перед записью конфигурации UI требует приостановить маршрутизацию.
  Не добавлять автоматическую остановку и повторный запуск при сохранении:
  это создаст неявное окно прямой передачи между экземплярами backend.
- Реализация пока экспериментальная. Поддерживать актуальными ограничения
  и статус интеграционной проверки в `README.md`; не объявлять backend
  проверенным без изолированных сквозных сетевых тестов.

### Общие правила разработки

- Общаться с пользователем по-русски, если он не попросил другой язык.
- Делать работающие вертикальные срезы: настройка в UI → сохранение →
  применение сетевым слоем → проверка фактического поведения.
- Не подменять реальный перехват трафика демонстрационными переключателями,
  фиктивной статистикой и захардкоженными успешными статусами.
- Для сетевых изменений проверять как минимум затронутые сценарии TCP,
  UDP, DNS, порядок правил, отказ прокси и остановку приложения.
- Проверки, изменяющие маршруты или перехватывающие реальные соединения
  пользователя, выполнять в изолированной среде либо после явного согласования.
- Различать проверенные функции, реализованные, но не проверенные интеграционно
  функции и запланированные возможности. Указывать существенные ограничения.
- Поддерживать воспроизводимую сборку `.exe` и документировать команды
  разработки, сборки и запуска по мере появления реализации.

### Редактор и соединения

- Условия маршрута редактируются списками. Выбор процессов выполняется по запросу
  через Toolhelp snapshot, без фонового опроса. В профиль сохранять имя EXE или путь,
  а не PID; PID в выборе только справочный. Поддомены задаются только явным *.,
  без отдельной галочки. При первом чтении профиля версии 1 перевести точные
  домены в суффиксы по запросу пользователя, сохранить исходный профиль рядом
  как config.v1-backup-N.json и атомарно записать версию 2. Новые точные домены
  версии 2 автоматически не расширять.
- Высоту содержимого длинной формы считать по preferred-height, с нижним отступом;
  проверять прокрутку колесом и первый клик по последнему полю.
- Соединения показывать единым раскрывающимся списком по EXE (все экземпляры вместе),
  фильтровать по процессу и тексту, сохранять раскрытие при обновлении статистики.
  Активные сеансы и байты учитывать для SOCKS; вложенные события —
  по ограниченному журналу. Не называть число событий числом живых соединений.
- Метрики ограничены 512 группами процессов, журнал — 256 событиями. Обновлять UI
  только при видимом окне. Очистка журнала не сбрасывает активные сеансы и байты.
- routing_enabled хранит последнее состояние тумблера. Сохранять ручную паузу
  сразу при переключении, восстанавливать ее после выхода, при подтвержденной
  ошибке сетевого слоя запоминать выключенное состояние. Обычный выход не
  заменяет сохраненное включенное состояние выключенным при остановке backend.
- Общий логотип для EXE, окна и трея. Зеленая точка в трее появляется только после
  подтвержденного запуска backend, красная означает выключение или ошибку;
  причину ошибки показывать в tooltip/UI. Рендерер логотипа: src/branding.rs.

- По запросу пользователя настройки автозапуска управляют собственной задачей
  Планировщика Windows с InteractiveToken/HighestAvailable и --tray; не менять
  другие задачи и не добавлять --enable. Состояние маршрутизации берется из профиля.
- Проверки доступности SOCKS выполняются каждые 30 секунд вне UI/поточного backend,
  не более четырех автоматически одновременно. Preview/smoke не проверяет сеть
  и не регистрирует автозапуск; тест задачи проверяет XML только в памяти.

  согласно Royalty-free License 2.0 §2(b); сохранять официальный badge на этих страницах.
